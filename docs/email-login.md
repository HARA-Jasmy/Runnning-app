# パスワードログインとメール確認付き登録

初期画面はメールアドレスと「PDLでログイン」「新規登録」の2ボタン。
- ログイン: パスワード入力へ進み、signInWithPasswordで認証。メールは送らない。
- 新規登録: パスワード・確認入力→signUp→確認メール→登録完了。
- 旧メールリンク方式でパスワード未設定の利用者: ログイン中の端末のマイページ→設定→パスワードを設定・変更。
- ログインできない場合: ログイン画面の「パスワードを忘れた・まだ設定していない方」から明示的に再設定メールを送る。
  recoveryリンクでセッションを復元し、パスワード設定フォームを開く。
- 通常ログインにメール送信はない。登録・再設定メールの既存レート制限は解除しない。

認証メール・再設定メールの戻り先はhttps://jasmy-running-app.vercel.app/に固定。
SupabaseのSite URL/Redirect URLsも同じ値が必要。メール確認は有効のまま。
パスワードをアプリ側で保存・ログ出力しない。Supabase Authに渡す。
PDLボタンという名称はUI上のもの。実認証はSupabase Authであり、Jasmy PDLの公式API接続は別途必要。

検証: SDKモックによるログイン時のメール非送信、登録の認証先、入力エラー、再設定の戻り先をテスト。
実在アドレスへのメール送信や、利用者のパスワードによるログインはテストしない。

## 登録受付とメール認証の区別

新規登録の応答だけでは、メール到着や本人の確認操作を証明できません。登録済みアドレスへの応答も含めて「登録リクエストの受付」と表示し、ログイン・再設定へ進めます。再設定も到着を断定しません。

新規登録前に公開 Auth settings の `mailer_autoconfirm` が `false` であることを確認します。設定が確認できない場合は登録を停止します。予期せず signup からセッションが返った場合は、そのローカルセッションを破棄してエラーを表示します。このチェックはアプリ側の防御であり、Supabase 側の Confirm email 設定を代替しません。

送信制限、送信先制限、サービス側エラーを分けて表示します。認証済みの日時や AMR の otp/password 記録は、メールが受信箱へ到達した証明や操作した本人の証明にはなりません。調査で既存利用者の認証状態・パスワード・走行記録を変更しません。
